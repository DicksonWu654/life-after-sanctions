# EVM histories: sources, reconstruction, and limits

EVM source artifacts include `scripts/fetch/evm/`, `data/raw/evm/`, the eight EVM timeline directories and `data/bootstrap/fetch_evm.csv`. Numeric run results are generated by `scripts/fetch/evm/validate.py` into `data/raw/evm/reports/validation.json.gz` and `coverage.json.gz`. The final coverage table is appended to this document after acquisition.

## Input and provenance

The fetcher accepts `--addresses data/addresses.csv` without conversion, using `chain,address_normalized` or `chain,address`. Chain names are case insensitive. All valid 20-byte `0x` addresses receive ETH, BSC, Arbitrum, Polygon, Base, and Optimism checks, in addition to any listed ETC or Avalanche C chain. A non-listed chain is explicitly marked `same address, other chain`; it is not another OFAC designation. Invalid address shapes are not sent to a node.

Before the ledger existed, `bootstrap.py` downloaded data files from the **lists branch** of [0xB10C's address extraction](https://github.com/0xB10C/ofac-sanctioned-digital-currency-addresses/tree/lists), pinned to a commit SHA. Its default main branch does not contain the lists. The bootstrap also unions the ETH snapshot immediately before 2025-03-21, preserving historical, delisted Tornado Cash addresses. Historical inclusion is not a statement of current designation. Raw GitHub commit/tree/list responses and pinned URLs are under `data/raw/evm/bootstrap/`; `provenance.json.gz` identifies the exact revisions. No upstream code was downloaded or executed. OFAC's ledger, when available, supplies designation dates and controls the final address inventory.

## History APIs

- [Etherscan v2](https://docs.etherscan.io/): account `txlist`, `txlistinternal`, and `tokentx`. NFT endpoints are excluded. Request starts are serialized across collector processes to at most one per 0.6 seconds (1.67 requests/second), below its 2.5 request/second allocation. This was reduced from 2.23 requests/second after saved responses reported a shared-key 3/second limit. The key is loaded at runtime from `ETHERSCAN_API_KEY` in the process environment and is excluded from cache identities and saved request metadata; exact occurrences are redacted from responses and errors before saving.
- Keyless [Blockscout](https://docs.blockscout.com/devs/apis) supplies fallback histories. Native v2 address `transactions`, `internal-transactions`, and ERC20 `token-transfers` endpoints use opaque `next_page_params` cursors; Optimism's v2 endpoints worked while its Etherscan-compatible endpoints persistently returned HTTP 429. ETC's compatible endpoint was also checked. Rate-limit responses, including JSON-RPC rate errors inside HTTP 200, trigger bounded exponential retry, shared host cooldown, and slower subsequent requests. Provider error responses are retained as evidence.
- [Routescan](https://docs.routescan.io/): an additional Etherscan-compatible fallback, with public Avalanche C support checked. Unsupported chains are retained as source gaps rather than treated as empty accounts.
- Public RPCs provide `eth_blockNumber`, `eth_getBlockByNumber`, `eth_getBalance`, `eth_getTransactionCount`, `eth_getCode`, and ERC20 `balanceOf` calls at an explicitly recorded block. Endpoint configuration is in `chains.py`. PublicNode's older-state restrictions were observed even for recent L2 blocks; alternative public endpoints are configured where tested. Optimism rejects batches over ten items; Base also limits RPC-item throughput. Their snapshot groups and token batches respect those limits. Node failures remain missing observations, never zero substitutions. ETC's address API supplies its reported balance when the RPC bridge reports `Balance not found`, with the reported update block kept distinct from the history head.

The observed Etherscan plan permits ETH, Arbitrum, and Polygon. It rejects BSC, Base, Optimism, and Avalanche C as requiring a paid plan, and does not support ETC. Saved plan-rejection responses are under `data/raw/evm/etherscan/`. Routescan reports BSC/Base unsupported. Base Blockscout returned HTTP 403. These restrictions leave explicit history gaps wherever no fallback succeeds.

Requests ask for ascending block ranges. A response containing **1,000 or more records is treated as potentially capped**, even if the requested offset is 10,000: observed free-tier responses silently clamp their effective size. The next request begins at the last returned block, and that boundary block is refetched in full. Records before the boundary are retained once. A single block containing at least 10,000 records is reported as a gap. This avoids the 10,000-result window and the observed 1,000-result cap without assuming a short response proves a full requested page was honored.

The default budget is 600 requests per address/action. If exhausted or a request fails, the precise unacquired block range is saved; designation windows T−60 through T+400 days and the latest 90 days are separately attempted and labeled complete/incomplete. Dates come from the ledger rather than guesses. Source outages may prevent those windows, too. Incomplete histories cannot support a claim of no movement.

Reconciliation also checks relationships between the acquired lists. The large auxiliary Tornado router had normal transactions absent from its acquired Etherscan normal-history responses but named by its internal-transfer history. `reconcile_rpc.py` audits those outer hashes with canonical `eth_getTransactionByHash` and receipts, adds only transactions directly involving the address, and preserves both RPC and timestamp evidence. Its saved audit is `data/raw/evm/reports/rpc_reconciliation.json.gz`. A finished pagination window alone is not an independent proof that an explorer index is complete.

## Tornado pool contracts

An on-chain interface check requires `denomination()` and `nextIndex()`, then distinguishes ERC20 pools through `token()`; native ETH pools revert on `token()`. Each result has a raw reference. A transport failure does not route a possible pool into ordinary transaction acquisition.

Pools use archive RPC [MEV Blocker](https://rpc.mevblocker.io) rather than Etherscan txlist. Full `Deposit(bytes32,uint32,uint256)` and `Withdrawal(address,bytes32,address,uint256)` logs are requested with adaptive block-range splitting on result-size errors. Event signature hashes are computed through `web3_sha3` and saved. The pool's `nextIndex()` is an independent check on the Deposit log count. A request budget or source failure leaves explicit missing log ranges.

One directly observed block per UTC date, beginning 2019-01-01 and ending on the last complete UTC day at the fetch head, is shared across the pools. A coarse block grid is followed by interpolation between observed timestamps to fill missing calendar dates. **These are daily samples at their actual block timestamps, not midnight or closing balances.** Each sample has a block response reference and RPC response ID. Archive `eth_getBalance`, and ERC20 `balanceOf` where applicable, supply independent daily asset balances. Pre-deployment dates can correctly show zero. The series is not derived from pool-event counts and is not a designation checkpoint calculation.

Deposit events contain an exact timestamp. Raw RPC Withdrawal logs do not: acquisition initially leaves `time_utc` null and supplies lower/upper timestamp bounds from adjacent observed daily blocks. `enrich_times.py` then obtains exact block timestamps through Etherscan's **getLogs** endpoint, joining by block number and checking the block hash against the authoritative RPC log. It never requests pool txlist. The raw log retains exact block and log index. Any unresolved timestamp stays null and is enumerated in `timestamp_coverage`; an interval bound is never presented as an exact time. Recipients and the indexed relayer are read from the event ABI; deposit senders are left unknown unless evidenced.

`pool_validation` compares `(Deposit count − Withdrawal count) × denomination` to the underlying asset's observed balance. The difference is reported in integer base units. Additional funds outside that principal model, nonstandard token behavior, or omitted event ranges can cause differences; an exact causal transaction is not inferred. `nextIndex` and log completeness are checked independently. Whole-address `coverage.complete` remains false for this deliberately scoped pool path, while `pool_events_complete` and `daily_balances_complete` state the pool-specific result. Unrelated tokens, donations, administration transactions, and ERC20-pool ETH refunds are outside the principal-event history.

## Timeline and raw contract

`data/timelines/<chain>/<lowercase-address>.json.gz` contains chain/address, fetch time, source descriptors, OFAC-listed chains, the same-address relationship, coverage, `txs`, `balance_now`, and errors. Native assets use the native ticker; tokens use their contract address as the asset key, with symbol and decimals recorded separately. Amounts are exact decimal strings, backed by integer `amount_raw`. No USD valuation is performed here.

External, internal, and ERC20 records are distinct `kind` values. A failed external transaction contributes zero transferred value but keeps the sender's fee. Internal transfers and token records do not charge that fee again. Self transfers affect only fees. Normal contract-creation transfers use the creation address when the API's `to` is empty. The fetcher preserves duplicate token logs in a single transaction when an API omits `logIndex`, while deduplicating overlapping acquisition windows by occurrence ordinal. API token symbols/metadata and transfers may contain spam; acquisition does not establish token value or issuer identity.

Each raw gzip stores a sanitized request, retrieval time, HTTP status, and response. Its filename hashes the key-free request. `raw_ref` identifies the file plus JSON pointer where available; RPC batches additionally use `rpc_response_id`. Successful immutable ranges are cached. Failed attempts have independent observation filenames, including semantic errors returned with HTTP 200; legacy error cache entries are preserved before replacement. Historical source errors are not cached as successful results. ERC20 balances must be one ABI uint256 word: pathological responses and out-of-range spam integers become explicit asset errors rather than aborting the address or inventing a balance. The fetcher uses only Python's standard library, so no new dependencies or shared requirements edits were needed.

The token balance inventory is native coin plus token contracts observed in ERC20 history and configured stablecoin contracts. Where history is unavailable, this does not enumerate all assets the address may hold. Symbols are API metadata, and a token using a familiar symbol is not thereby identified with an issuer.

## Running and validation

```sh
.venv/bin/python scripts/fetch/evm/bootstrap.py
.venv/bin/python scripts/fetch/evm/fetch.py --addresses data/addresses.csv
.venv/bin/python scripts/fetch/evm/fetch.py --addresses data/addresses.csv --refresh
.venv/bin/python scripts/fetch/evm/enrich_times.py
.venv/bin/python scripts/fetch/evm/repair_balances.py --chains eth,arb,polygon,base,op
.venv/bin/python scripts/fetch/evm/repair_balances.py --chains bsc --latest
.venv/bin/python scripts/fetch/evm/fetch.py --check
.venv/bin/python scripts/fetch/evm/reconcile_rpc.py --address 0xd90e2f925da726b50c4ed8d0fb90ad053324f31b
.venv/bin/python scripts/fetch/evm/reconcile_tokens.py
.venv/bin/python scripts/fetch/evm/fetch.py --check
.venv/bin/python scripts/fetch/evm/report.py
.venv/bin/python -m unittest discover -s scripts/fetch/evm -p 'test_*.py' -v
```

A completed history rerun reuses history and checks only head/state/balances. Provider capabilities are persisted to avoid repeating history probes. `--refresh` begins after each action's covered block, keeping older records. Incomplete ranges can be resumed against their immutable saved head without refetching successful raw pages. Version-1 acquisitions, which predated the effective-page-size correction, are explicitly revalidated under schema version 2. Daily block observations and completed pool balances are reused. Per-chain OS locks prevent concurrent EVM commands from rewriting the same chain. Chain RPC state pruning can still require endpoint repair; `repair_balances.py` measures state at the timeline's exact history end to make arithmetic checks conclusive, retaining the explicit observation block/time. Its `--latest` mode uses a fresh pinned head per small address group for nodes that retain only recent state.

`--check` performs no network requests. It checks normalized units, direction, bounds, schema, referenced files, the full bootstrap and ledger address/chain matrix, and balance arithmetic across available assets. Its mandatory sample includes the three largest nonempty ordinary ETH histories and twelve additional ordinary ETH addresses; every identified pool is checked separately. `validation.json.gz` reports every address/asset check, separating exact matches, mismatches, and comparisons with incomplete history or different blocks. A structurally valid dataset is not a claim that all financial checks matched. Every pool has an additional contract validation record. `coverage.json.gz` enumerates every timeline, missing input pair, and malformed input address without silently correcting OFAC's string.

`reconcile_tokens.py` explains observed WETH differences by independently acquiring its Deposit/Withdrawal supply events: these mints and burns are outside WETH9's Transfer-event list. Raw differences remain visible alongside an explicitly separate adjustment, used only at the same history/balance block. A bounded audit of eight other token contracts compares all Transfer logs in an example block against archive `balanceOf` before/after that block; observed differences demonstrate that Transfer-only accounting does not equal state changes there. This does not invent a present-day adjustment or attribute control of the token. The evidence and remaining unresolved causes are under `data/raw/evm/reports/reconciliation_causes.json.gz` and linked from each affected validation check.

For every pool, validation also compares daily principal-event totals with each independent archive balance at the same block. Missing pre-deployment token observations are not filled with zero. The check validates chronological sample order, unique dates, event counts against `nextIndex`, and recipient/relayer amount splits. The mandatory ordinary-address sample must contain fifteen conclusive native-ETH matches for `--check` to pass; token exceptions remain explicitly reported.
